OSL Integration Roadmap

💡 Identity & Direction of OSL Integration

OSL Integration is a "Modular Backend Infrastructure & Architecture Suite" optimized for the Unity Asset Store. Each package functions independently (decoupled) so developers can pick only what they need, while still gaining synergy when modules are used together.

  • Zero-Loss-Oriented Reliability: Offline queueing, resumable downloads, and automatic sync patterns to reduce data or payment loss in unstable environments.
  • Server-Authoritative Security: Server-side IAP validation, token verification, and Cloud Code validation to reduce client-side tampering and cheating risks.
  • Unity Asset Friendly (DX): Editor diagnostic tooling, one-click server deployment paths, and simple mock providers tailored for Unity developers who need backend workflows without heavy server knowledge.

Package structure note: OSL Integration currently contains 7 deliverable packages organized into 6 roadmap tracks. SocialLoginPro is a bundled distribution package combining SocialLogin and TokenVerification; it is not maintained as a separate feature roadmap track.

🧭 Roadmap Operating Rules

  1. Each package's Priority 1 items map to Phase 1, Priority 2 items map to Phase 2, and Priority 3 items map to Phase 3 by default.
  2. Phase 1 is not about adding as many features as possible. It is about making each package reliable, recoverable, and diagnosable inside real Unity projects.
  3. Phase 2 adds optimization, testing convenience, and advanced validation logic on top of stable Phase 1 workflows.
  4. Phase 3 covers higher-maintenance expansions such as UI templates, console platforms, admin dashboards, and custom backend integrations.
  5. Before implementation, always inspect existing code and changelogs to avoid re-implementing already completed features.
  6. Agents must review Current Focus and the target package's Done Criteria before starting work.
  7. Current Focus is the current execution order. Sort priority is new-version upload value → improvement impact → low demo/test burden.
  8. Items marked 🚀 Release Candidate can be treated as new version upload candidates after implementation, testing, changelog, package version, and export validation are complete.
  9. Items marked 🧪 Lightweight Validation do not require a new demo scene or can be verified mostly through editor, unit, or API tests.

Phase 1 Done Criteria:

  • Payment, save, and patch workflows must be recoverable after network interruption, app restart, or reconnection.
  • At least one sample or test must validate each critical failure scenario.
  • Configuration mistakes must be diagnosable through Editor tooling or clear logs.
  • 🚀 Release Candidate items are only considered upload candidates after changelog and package version updates are also complete.

Phase 2 Done Criteria:

  • New optimization features must not weaken Phase 1 reliability.
  • Advanced features should be optional, feature-flagged, or able to fall back to the stable base flow.
  • Documentation and tests must be added together with advanced features.

Phase 3: Long-term / On Hold (UI & External Integrations)

Goal: Consider sales-driven or expansion-focused features after the core modules are stable.

  • Platform Expansion: OneStore (IAP), Xbox/PSN (SocialLogin), custom backends.
  • UI & Frontend: Drop-in social login/store UI prefabs, Admin Dashboard web apps.
  • Deterministic Expansion: Deterministic 2D/3D Noise, Fixed-Point Math Library.
  • EasyPatcher Expansion: In-game patch notes UI, native mobile OS background download integration.

Phase 3 Done Criteria:

  • Start only after core module reliability is sufficiently proven.
  • Prioritize UI/platform expansions based on actual sales signal, user requests, or usage frequency.
  • Treat breaking API or package-structure changes as possible major-version candidates.

1. Deterministic Core

Role

Provides deterministic RNG, gacha, combat probability, and state reproducibility foundations.

Current Weak Points / Risks

  • Reproducibility tests and state save/restore flows matter more than Burst/Job optimization at this stage.
  • Fixed-Point Math and Noise can expand the product scope too aggressively and increase maintenance cost.
  • Math/probability modules require strong tests before new feature expansion.

  • [ ] Add RNG state serialization convenience features

Done Criteria:

  • The sample must make synchronization failure clearly visible to the user.
  • Consider this a 1.1.0 release candidate after changelog, package version, and export validation are complete.

2. Token Verification

Role

Provides a backend template that verifies social login tokens/session tickets received from the Unity client.

Current Weak Points / Risks

  • For Unity developers, running and deploying the backend is the largest adoption barrier.
  • Deployment convenience, baseline security middleware, and error diagnostics should come before adding more provider features.
  • If a provider already exists according to the changelog, the roadmap should not list it again as a new provider-addition task.

Priority 1: Backend Reliability & Deployment Convenience 🚀 Release Candidate: TokenVerification 1.1.0 🧪 Lightweight Validation

  • [ ] Strengthen JWKS in-memory cache tests
  • [ ] Clean up self-contained executable and Visual Studio Publish Profile support
  • [ ] Add baseline Rate Limiting / request-size limits / common error response rules
  • [ ] Maintain .NET 8 support and track .NET 10 LTS compatibility path

Done Criteria:

  • The server must run locally through dotnet run or a self-contained executable.
  • JWKS cache refresh/expiration/failure cases must be observable through tests or logs.
  • Invalid requests must return consistent error responses.
  • Consider this a 1.1.0 release candidate after changelog, package version, and export validation are complete.

Priority 2: Provider Validation Hardening 🚀 Release Candidate: TokenVerification 1.2.0

  • [ ] Organize provider-specific validation options
  • [ ] Add structured audit-log format
  • [ ] Improve Rate Limiting policies

Priority 3: Long-term Expansion

  • [ ] Admin Dashboard web app for token verification logs
  • [ ] Custom JWT issuance (IdP) and session management system

3. Secure Save

Role

Routes Cloud Save write operations through UGS Cloud Code validation to provide a server-authoritative save workflow.

Current Weak Points / Risks

  • The phrase "offline save" can be misleading. The intended meaning is not saving to the server while offline, but storing writes in a Pending Write Queue and syncing them after reconnection.
  • UGS Cloud Code, Cloud Save, and Remote Config dependencies create many possible setup-failure points.
  • Conflict handling must be explicit to preserve user trust in saved data.

Priority 1: Pending Write Queue & Load Optimization 🚀 Release Candidate: SecureSave 1.1.0

  • [ ] Add Pending Write Queue and automatic synchronization
  • [ ] Define retry/failure/conflict handling policy
  • [ ] Add Multi-key selective load functionality

Done Criteria:

  • Writes made while offline must be processed in order after reconnection.
  • Failed writes must remain visible to the user or be safely retried.
  • Cloud Code validation failures and network failures must be distinguishable.
  • Consider this a 1.1.0 release candidate after changelog, package version, and export validation are complete.

Priority 2: Validation Rule Expansion 🚀 Release Candidate: SecureSave 1.2.0

  • [ ] Add Regex and Whitelist validation rules
  • [ ] Add Local Unit Testing Utility for Cloud Code scripts

Priority 3: Long-term Expansion

  • [ ] In-game GM Save Editor UI component
  • [ ] Custom backend integration module (non-UGS)

4. EasyPatcher

Role

Provides a lightweight Unity runtime patch system that downloads and verifies only changed files.

Current Weak Points / Risks

  • Binary Diffing is attractive but expensive and risky to maintain.
  • File-level resume, verification, and retry flows must be solid before delta patching.
  • Concurrent downloads are performance features, but they can amplify cache and failure-handling bugs if added too early.

Priority 1: Reliable Download Recovery 🚀 Release Candidate: EasyPatcher 1.2.0

  • [ ] HTTP Resumable Download support
  • [ ] SHA256/HMAC verification after download completion
  • [ ] Retry failed files independently
  • [ ] Add concurrent downloads only after the resumable flow is stable

Done Criteria:

  • Interrupted downloads must resume from partial files.
  • Resumed files must pass final hash/HMAC verification.
  • Failed files must be retryable independently.
  • Consider this a 1.2.0 release candidate after changelog, package version, and export validation are complete.

Priority 2: Patch Efficiency Optimization 🚀 Release Candidate: EasyPatcher 1.3.0 🧪 Lightweight Validation

  • [ ] Manifest (version.json) GZip/Brotli compression support
  • [ ] Add S3-compatible Custom Endpoint URL option
  • [ ] Delta Patching / Binary Diffing feasibility validation
  • [ ] Keep Binary Diffing behind a feature flag or experiment branch before promoting it to a core feature

Priority 3: Long-term Expansion

  • [ ] In-game patch notes UI component
  • [ ] Native mobile OS background download integration

5. IapClient

Role

Connects Unity IAP purchase results to backend validation before granting in-game rewards.

Current Weak Points / Risks

  • Payments have the highest failure cost. Duplicate reward prevention, loss prevention, and retry behavior matter more than extra features.
  • Local receipt validation must never replace server validation. It should only be used as a pre-check or UX helper.
  • Pending Receipt Queue must be designed together with transaction idempotency.

Priority 1: Payment Loss Prevention & Retry ✅ Completed 🚀 Release Candidate: IapClient 1.1.0

  • [x] Local queueing for Pending Receipts
  • [x] Exponential Backoff network retry logic
  • [x] Define transaction id / receipt-based idempotency rules
  • [x] Recover pending purchases after app restart

Done Criteria:

  • Rewards must not be lost when server validation or the network temporarily fails after purchase success.
  • The same transaction must not grant duplicate rewards.
  • Pending receipts must survive app restart and resume verification.
  • Consider this a 1.1.0 release candidate after changelog, package version, and export validation are complete.

Priority 2: Subscription & Local Validation Helpers 🚀 Release Candidate: IapClient 1.2.0

  • [ ] Subscription Status local caching with TTL
  • [ ] Client-side Local Receipt Validation option

Priority 3: Long-term Expansion

  • [ ] In-game storefront scrolling UI template
  • [ ] Third-party app store verification API integration (e.g., OneStore)

6. SocialLogin & SocialLoginPro

Role

SocialLogin provides a unified client-side interface for Apple, Facebook, Google, Steam, and Discord login flows. SocialLoginPro is a combined distribution package that includes SocialLogin and TokenVerification. It follows almost the same feature track as SocialLogin and should not become a separate duplicated implementation track.

Current Weak Points / Risks

  • Social login fails in many places: provider configuration, Manifest, Info.plist, Redirect URI, SDK availability, and build settings.
  • Diagnostic tooling can provide more buyer value than adding another provider too early.
  • SocialLoginPro should avoid duplicate code and remain a packaging/documentation/sample-level combination of SocialLogin and TokenVerification.

Priority 1: Core Usability & Diagnostics 🚀 Release Candidate: SocialLogin 1.2.0 / SocialLoginPro 1.3.0

  • [ ] Auto-Login and Token Refresh Manager
  • [ ] Editor Diagnostics Utility
  • [ ] Inspect Manifest, Info.plist, Redirect URI, and Provider configuration issues
  • [ ] Display Soft Dependency activation state

Done Criteria:

  • Missing setup must produce diagnostics before users hit compile errors or runtime failures.
  • Required Provider settings must be visible in the Editor.
  • SocialLoginPro must work as a SocialLogin + TokenVerification combination without a separate implementation roadmap.
  • Consider SocialLogin 1.2.0 and SocialLoginPro 1.3.0 release candidates after changelog, package version, and export validation are complete.

Priority 2: Testing Convenience 🚀 Release Candidate: SocialLogin 1.3.0 / SocialLoginPro 1.4.0

  • [ ] Mock Social Login Provider for Editor
  • [ ] Add sample flow for testing UI/UX without real providers

Priority 3: Long-term Expansion

  • [ ] Animated Drop-in Social Login UI prefab template
  • [ ] Console-specific platforms integration (Xbox Live, PSN, Epic Games)
