OSL Integration 로드맵

💡 OSL Integration의 정체성 및 개발 방향

OSL Integration은 유니티 에셋 스토어(Unity Asset Store) 환경에 최적화된 **"모듈형 백엔드 인프라 및 아키텍처 스위트"**입니다. 각 패키지는 프로젝트에 필요한 것만 골라 쓸 수 있도록 독립적(Decoupled)으로 동작하면서도, 통합해서 사용했을 때 강력한 시너지를 냅니다.

  • 유실 방지 지향 안정성 (Zero-Loss-Oriented Reliability): 오프라인 큐잉, 이어받기, 자동 동기화 패턴으로 불안정한 환경에서 데이터/결제 유실 위험을 줄임
  • 서버 권한 보안 (Server-Authoritative Security): 결제 영수증 검증, 토큰 검증, 클라우드 코드 기반 세이브 검증 등을 통해 클라이언트 변조 및 치팅 위험을 줄임
  • 유니티 에셋 친화적 경험 (DX): 서버 지식이 깊지 않아도 쉽게 쓸 수 있는 에디터 진단 툴링, 원클릭 서버 배포, Mock Provider 등을 제공

패키지 구조 참고: OSL Integration은 현재 7개 배포 패키지로 구성되며, 로드맵은 6개 주요 트랙 기준으로 관리합니다. SocialLoginPro는 SocialLogin과 TokenVerification을 결합한 번들형 배포 패키지이며, 별도의 기능 로드맵 트랙으로 분리하지 않습니다.

🧭 로드맵 운용 원칙

  1. 각 패키지의 1순위 항목은 Phase 1, 2순위 항목은 Phase 2, 3순위 항목은 Phase 3에 기본 대응합니다.
  2. Phase 1은 기능 수를 늘리는 단계가 아니라, 유저가 실제 프로젝트에 넣었을 때 깨지지 않게 만드는 신뢰성·복구성·진단성 확보 단계입니다.
  3. Phase 2는 이미 안정화된 흐름 위에 최적화, 테스트 편의성, 고급 검증 로직을 추가하는 단계입니다.
  4. Phase 3은 UI, 콘솔 플랫폼, 운영 대시보드, 커스텀 백엔드처럼 유지보수 부담이 큰 확장 기능을 다룹니다.
  5. 구현 전에는 항상 기존 코드와 Changelog를 먼저 확인하여 이미 완료된 기능을 다시 구현하지 않습니다.
  6. 에이전트는 작업을 시작하기 전 이 문서의 Current Focus와 해당 패키지의 완료 기준을 우선 확인합니다.
  7. Current Focus는 현재 시점의 실행 순서입니다. 정렬 기준은 새 버전 업로드 가치 → 개선 효과 → 데모/테스트 부담이 낮은 작업 순입니다.
  8. 🚀 출시 후보가 붙은 항목은 구현, 테스트, Changelog, 패키지 export 검증이 끝나면 새 버전 업로드 대상으로 볼 수 있습니다.
  9. 🧪 간단 검증이 붙은 항목은 새 데모씬 구현이 없거나, 에디터/유닛/API 테스트 중심으로 비교적 검증 부담이 낮은 작업입니다.

1. Deterministic Core

역할

결정론적 RNG, 가챠, 전투 확률, 상태 재현을 위한 기반 모듈입니다.

현재 아쉬운 점 / 리스크

  • 성능 최적화(Burst/Job)보다 먼저 재현성 검증과 상태 저장/복원 흐름이 더 중요합니다.
  • Fixed-Point Math나 Noise까지 확장하면 제품 범위가 커져 유지보수 부담이 급격히 증가할 수 있습니다.
  • 수학/확률 모듈은 작은 오류도 신뢰도를 크게 깎으므로 테스트가 기능보다 먼저입니다.

완료 기준:

  • 샘플에서 동기화 실패 여부를 유저가 명확히 확인할 수 있어야 합니다.
  • Changelog/package version/export 검증 완료 시 1.1.0 출시 후보로 판단합니다.

2. Token Verification

역할

Unity 클라이언트에서 받은 소셜 로그인 토큰/티켓을 자체 백엔드에서 검증하는 서버 템플릿입니다.

현재 아쉬운 점 / 리스크

  • Unity 개발자에게는 서버 실행/배포 자체가 가장 큰 진입 장벽입니다.
  • Provider 검증 로직보다 배포 편의성, 기본 보안 미들웨어, 에러 진단성이 먼저 필요합니다.
  • Changelog 기준으로 이미 구현된 Provider가 있다면, 로드맵에서 같은 Provider를 다시 "추가" 대상으로 두면 안 됩니다.

1순위: 백엔드 신뢰성 및 배포 편의성 🚀 출시 후보: TokenVerification 1.1.0 🧪 간단 검증

  • [ ] JWKS 인메모리 캐싱 테스트 보강

3. Secure Save

역할

UGS Cloud Code를 통해 Cloud Save 쓰기 요청을 검증하는 서버 권한 저장 모듈입니다.

현재 아쉬운 점 / 리스크

  • "오프라인 저장"이라는 표현은 오해의 소지가 있습니다. 실제 의미는 오프라인 중 서버 저장이 아니라, 재접속 후 서버 검증을 거쳐 처리할 Pending Write Queue입니다.
  • Cloud Code, Cloud Save, Remote Config 의존성이 있어 설정 실패 가능성이 높습니다.
  • 충돌 처리 정책이 명확하지 않으면 유저 데이터 신뢰성이 떨어집니다.

1순위: Pending Write Queue 및 로드 최적화 🚀 출시 후보: SecureSave 1.1.0

  • [ ] Pending Write Queue 및 자동 동기화 지원
  • [ ] 재시도/실패/충돌 처리 정책 정의
  • [ ] 선택적 키(Multi-key) 로드 기능 추가

완료 기준:

  • 오프라인 중 발생한 쓰기 요청이 재접속 후 순서대로 처리되어야 합니다.
  • 실패한 요청은 유저가 확인 가능한 상태로 남거나 안전하게 재시도되어야 합니다.
  • Cloud Code 검증 실패와 네트워크 실패가 구분되어야 합니다.
  • Changelog/package version/export 검증 완료 시 1.1.0 출시 후보로 판단합니다.

2순위: 검증 룰 고도화 🚀 출시 후보: SecureSave 1.2.0

  • [ ] Regex 및 Whitelist 검증 룰 추가

4. EasyPatcher

역할

Unity 런타임에서 변경 파일만 다운로드하고 검증하는 경량 패치 시스템입니다.

현재 아쉬운 점 / 리스크

  • Binary Diffing은 매력적이지만 난이도와 유지보수 부담이 매우 큽니다.
  • 먼저 파일 단위 이어받기, 검증, 재시도 흐름이 완성되어야 합니다.
  • 병렬 다운로드는 성능 기능이지만, 실패 처리와 캐시 정합성이 불안정하면 오히려 버그를 키웁니다.

완료 기준:

  • 중단된 다운로드가 partial file에서 재개되어야 합니다.
  • 재개 후 최종 파일 hash/HMAC 검증을 통과해야 합니다.

5. IapClient

역할

Unity IAP 결제 결과를 자체 백엔드 검증 후 보상 지급으로 연결하는 결제 안정성 모듈입니다.

현재 아쉬운 점 / 리스크

  • 결제는 실패 비용이 가장 큰 영역입니다. 기능보다 중복 지급 방지, 유실 방지, 재시도가 먼저입니다.
  • 로컬 영수증 검증은 서버 검증을 대체하면 안 됩니다. 사전 필터 또는 UX 개선 용도로만 사용해야 합니다.
  • Pending Receipt Queue는 반드시 transaction idempotency와 함께 설계해야 합니다.

1순위: 결제 유실 방지 및 재시도 ✅ 완료 🚀 출시 후보: IapClient 1.1.0

  • [x] 미처리 결제건(Pending Receipt) 로컬 큐잉
  • [x] 지수 백오프(Exponential Backoff) 기반 네트워크 재시도
  • [x] transaction id / receipt 기반 idempotency 기준 정리
  • [x] 앱 재시작 후 미처리 결제 복구 흐름 추가

완료 기준:

  • 결제 성공 후 서버 검증 실패/네트워크 실패 시 보상 지급이 유실되지 않아야 합니다.
  • 동일 transaction이 중복 보상으로 이어지지 않아야 합니다.
  • 앱 재시작 후에도 pending receipt가 복구되어야 합니다.
  • Changelog/package version/export 검증 완료 시 1.1.0 출시 후보로 판단합니다.

2순위: 구독 및 로컬 검증 보조 기능 🚀 출시 후보: IapClient 1.2.0

6. SocialLogin & SocialLoginPro

역할

SocialLogin은 Apple, Facebook, Google, Steam, Discord 로그인 흐름을 통합 인터페이스로 제공하는 클라이언트 모듈입니다. SocialLoginPro는 SocialLogin과 TokenVerification을 함께 제공하는 조합형 배포 패키지이며, SocialLogin과 거의 같은 기능 트랙을 따릅니다.

현재 아쉬운 점 / 리스크

  • 소셜 로그인은 Provider별 설정, Manifest, Info.plist, Redirect URI, SDK 유무에 따라 실패 지점이 많습니다.
  • 실제 기능보다 "왜 로그인이 안 되는지"를 알려주는 진단 도구가 더 큰 구매 가치를 만들 수 있습니다.
  • SocialLoginPro는 별도 기능을 중복 구현하지 말고, SocialLogin과 TokenVerification을 올바르게 조합하는 패키징/문서/샘플 수준에서 관리해야 합니다.

1순위: 핵심 사용성 및 진단 🚀 출시 후보: SocialLogin 1.2.0 / SocialLoginPro 1.3.0

  • [ ] 자동 로그인(Auto-Login) 및 토큰 갱신 매니저 추가
  • [ ] 에디터 환경 진단(Diagnostics) 유틸리티
  • [ ] Manifest, Info.plist, Redirect URI, Provider 설정 누락 검사
  • [ ] Soft Dependency 활성화 상태 표시

완료 기준:

  • 설정 누락 시 컴파일 에러보다 진단 메시지가 먼저 제공되어야 합니다.
  • Provider별 필수 설정 상태를 에디터에서 확인할 수 있어야 합니다.
  • SocialLoginPro는 별도 구현 트랙 없이 SocialLogin + TokenVerification 조합으로 동작해야 합니다.
  • Changelog/package version/export 검증 완료 시 SocialLogin은 1.2.0, SocialLoginPro는 1.3.0 출시 후보로 판단합니다.
