Folder Management Rules

1. Purpose

This document defines the folder structure and rules for managing internal documentation and Unity Asset Store submission assets within the docs directory.

  • Note: All root management documents are maintained in two versions: English (_EN.md) for AI agents, and Korean (_KO.md) for developers.

2. Directory Structure

2.1. Root Directory (/docs/)

The root directory is strictly reserved for global project management documents that apply to all packages.

  • Project_Overview_EN.md: Project goals and high-level descriptions.
  • Roadmap_EN.md: Long-term milestones and current status.
  • Project_Rules_EN.md: Collaboration and coding guidelines.
  • Work_Log_EN.md: Daily/Weekly task logs.
  • Folder_Management_Rules_EN.md: This document.

2.2. Package Directories (/docs/{PackageName}/)

Each isolated Unity asset package must have its own subdirectory. These folders contain store-ready documentation and submission metadata.

Required Files:

  1. Summary.md: Short description for the asset store. Must be under 200 characters.
  2. Description.md: Long description including features and requirements.
  3. Technical_details.md: Technical specifications and algorithms used.
  4. Changelog.md: Release notes following a consistent Semantic Versioning-style format.
  5. Submission_Comments.md: Notes to the Asset Store reviewer.

3. Maintenance Rules

  • Always update the package Changelog.md before initiating an export for the Asset Store.
  • All package-specific files must be written in English to comply with Unity Asset Store guidelines.
  • Do not place binary files (images, PDFs) directly in these markdown directories unless strictly necessary for internal preview; prefer the project's actual Documentation/ or Documentation~ folder for user-facing PDFs.
  • Keep package-count terminology consistent: OSL Integration has 7 deliverable packages organized into 6 roadmap tracks, with SocialLoginPro treated as a bundled package combining SocialLogin and TokenVerification.
  • Keep Unity and backend compatibility wording evidence-based. Prefer Minimum Unity Version, Tested Unity Versions, and supported .NET LTS language over broad absolute claims.
  • Reviewer instructions must use the same menu names and file paths as the actual package, especially Tools > OSL > ..., Samples/ or Samples~/, and Server~/.
