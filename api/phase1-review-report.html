Findings

P1. SiteRuleConfig 캐시 객체가 요청 간 오염될 수 있음

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Rules/SiteRuleEngine.cs
  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReaderService.cs

문제

SiteRuleEngine은 host별로 SiteRuleConfig 인스턴스를 ConcurrentDictionary에 캐시합니다. 그런데 ReaderService에서 요청 파라미터 disable_css가 들어오면 캐시에서 받은 ruleConfig.BlockCss 값을 직접 변경합니다.

이 구조에서는 한 사용자의 요청 override가 같은 host를 사용하는 이후 요청에도 남을 수 있습니다.

영향

  • 특정 host에 대해 disable_css=true 또는 false가 한 번 적용되면 다음 요청의 동적 렌더링 resource blocking 정책이 의도와 다르게 동작할 수 있음
  • 요청 간 상태 격리 원칙 위반
  • 동적 스크래핑 품질과 비용 예측이 흔들릴 수 있음

수정 방향

  • SiteRuleEngine.ResolveConfig()가 캐시된 원본 config를 그대로 반환하지 않도록 복사본을 반환합니다.
  • 또는 SiteRuleConfig를 immutable record로 바꾸고, 요청별 override는 with 복사로 처리합니다.
  • 최소 수정안:
    • ResolveConfig 내부 캐시는 유지
    • 반환 시 CloneSiteRuleConfig(cachedConfig) 형태로 새 인스턴스 반환
    • ReaderService는 복사본에만 DisableCss override 적용

P1. 응답 캐시 키가 OutputOptions를 충분히 반영하지 않음

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReaderService.cs

문제

현재 cache key에는 다음 값들이 포함되지 않습니다.

  • Output.Content
  • Output.Metadata
  • Output.Tables
  • Output.CodeBlocks
  • Output.Images
  • Output.Links
  • DisableCss

하지만 실제 응답 내용은 이 옵션들에 따라 달라집니다. 예를 들어 첫 요청이 output_images=false로 캐시된 뒤, 이후 같은 URL을 output_images=true로 호출하면 기존 캐시 응답이 재사용될 수 있습니다.

특히 HTTP 304 Not Modified 응답이 오면 cachedObj를 그대로 반환하기 때문에 옵션이 다른 요청에서도 이전 응답 구조가 그대로 나갈 수 있습니다.

영향

  • API 사용자가 요청한 output option과 다른 결과를 받을 수 있음
  • metadata=false 요청 결과가 metadata=true 요청에 재사용될 수 있음
  • 이미지, 링크, 테이블, 코드 블록 포함 여부가 캐시 순서에 따라 달라지는 비결정적 동작 발생

수정 방향

  • 단기적으로는 cache key에 모든 출력 옵션과 DisableCss를 포함합니다.
  • 더 나은 구조는 캐시를 두 계층으로 분리하는 것입니다.
    • Raw fetch cache: URL, ETag, Last-Modified, HTML 원문
    • Rendered response cache: URL, output format, tokenizer, chunking, mode, output options
  • HTTP conditional request는 raw fetch cache 기준으로 처리하고, public response는 요청 옵션 기준으로 매번 렌더링하거나 별도 캐시합니다.

P1. 내부 캐시 메타데이터가 public API 응답에 노출될 수 있음

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Domain/Models/ReaderResponse.cs
  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReaderService.cs

문제

ReaderMetadata에 추가된 ETag, LastModified는 JsonPropertyName("_cache_etag"), JsonPropertyName("_cache_last_modified")로 이름만 변경되어 있습니다. 값이 null이 아니면 public API 응답 JSON에 그대로 직렬화됩니다.

현재 ReaderService는 metadata output 여부와 관계없이 캐시 검증 헤더를 항상 세팅하므로, 실제 응답에 _cache_etag, _cache_last_modified가 노출될 수 있습니다.

영향

  • 내부 인프라 상태가 public API 계약에 섞임
  • Output.Metadata=false의 의미가 더 모호해짐
  • RapidAPI 문서/사용자 응답 스키마와 실제 응답이 불일치할 수 있음

수정 방향

  • API 응답 DTO와 캐시 저장 DTO를 분리합니다.
  • 예시 구조:
    • ReaderResponse: public API 응답 전용
    • CachedReaderEntry: ReaderResponse Response, string? ETag, string? LastModified, DateTimeOffset CachedAt
  • 응답 반환 직전에는 내부 캐시 필드가 절대 포함되지 않도록 합니다.
  • 임시 대응으로 [JsonIgnore]를 붙이면 public 응답 노출은 막을 수 있지만, 같은 serializer를 Redis 저장에도 쓰면 캐시 헤더가 저장되지 않으므로 DTO 분리가 더 안전합니다.

P2. 중첩 테이블 row가 외부 테이블 data row로 렌더링될 수 있음

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReadabilityFilter.cs

문제

ProcessTableNode에서 .//thead//tr, .//tr[not(ancestor::thead)]를 사용합니다. 이 XPath는 현재 테이블의 직접 row뿐 아니라 중첩 테이블 내부 row까지 선택할 수 있습니다.

RenderTableRow에서 column selector를 ./th | ./td로 제한한 것은 좋은 수정이지만, row 수집 단계에서 이미 nested row가 포함될 수 있습니다.

영향

  • 외부 테이블 markdown에 내부 테이블 row가 별도 data row처럼 추가될 수 있음
  • 컬럼 수 계산은 일부 개선되었지만, nested table 구조의 행 분리 오류는 남을 수 있음

수정 방향

  • row 선택을 직접 자식 중심으로 제한합니다.
  • 예시:
    • ./thead/tr
    • ./tbody/tr
    • ./tr
  • tbody가 없는 브라우저 보정 HTML도 고려해서 직접 자식 row와 section row를 함께 처리합니다.

P2. 기존 핵심 사이트 룰은 여전히 Contains 기반 매칭을 사용함

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Rules/DefaultRules.cs
  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Rules/DomainMatchSiteRule.cs

문제

신규 사이트 룰은 DomainMatchSiteRule을 통해 host 기반 매칭을 사용하지만, 기존 핵심 룰인 Coupang, Amazon, MDN은 여전히 url.Contains(...) 방식입니다.

예를 들어 https://example.com/redirect?to=amazon.com 같은 URL이 Amazon 룰로 오탐될 수 있습니다.

영향

  • 경로 또는 query string에 포함된 도메인 문자열로 잘못된 rule이 선택될 수 있음
  • proxy strategy, dynamic/static strategy, timeout, resource blocking 설정이 엉뚱하게 적용될 수 있음
  • "정확한 도메인 매칭"이라는 구현 목표와 실제 동작이 불일치

수정 방향

  • CoupangSiteRule, AmazonSiteRule, MdnSiteRule도 DomainMatchSiteRule을 상속하도록 변경합니다.
  • Amazon은 amazon.com, amazon.co.jp, amazon.co.uk 등 허용 host 목록을 MatchHosts로 명시합니다.
  • DomainMatchSiteRule의 주석 중 github.com이 raw.githubusercontent.com도 매칭된다는 설명은 실제 로직과 맞지 않으므로 수정합니다. 현재 로직은 api.github.com은 매칭하지만 raw.githubusercontent.com은 매칭하지 않습니다.

P2. Inline code 주변 공백이 깨질 수 있음

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReadabilityFilter.cs

문제

Text node 처리에서 Trim()을 사용하고, inline <code>는 앞뒤 공백 없이 backtick으로 감쌉니다.

예를 들어 아래 HTML은:

<p>Use <code>x</code> here</p>

다음처럼 붙어서 나올 가능성이 있습니다.

Use`x`here

영향

  • 마크다운 가독성 저하
  • 코드 토큰 주변 문장 의미가 변형될 수 있음
  • LLM/RAG 입력 품질 저하

수정 방향

  • text node의 leading/trailing space를 무조건 제거하지 않고, inline 흐름에서는 필요한 공백을 보존합니다.
  • inline 요소 앞뒤에 EnsureSpaceIfNeeded 같은 helper를 적용합니다.
  • block 요소 내부에서는 최종 normalize 단계에서 과도한 공백만 정리합니다.

P3. Code fence 분리 로직이 본문 안의 triple backtick에 취약함

관련 파일

  • src/Services/Scraper/OngsooLabs.Scraper.Infrastructure/Services/ReadabilityFilter.cs

문제

CollapseNewlinesOutsideCodeBlocks는 markdown 전체를 단순히 ``` 문자열로 split합니다. 코드 내용 자체에 triple backtick이 포함되면 inside/outside 판단이 깨질 수 있습니다.

영향

  • 코드 블록 내부 공백 보존이 의도와 다르게 동작할 수 있음
  • 드물지만 문서형 사이트나 Markdown tutorial 문서에서 발생 가능

수정 방향

  • line 단위 state machine으로 fence 시작/종료를 판별합니다.
  • fence marker는 line start 기준으로만 인식합니다.
  • 코드 내용에 포함된 inline triple backtick과 block fence를 구분합니다.

Recommended Fix Plan

Step 1. 캐시/API 계약 안정화

우선순위가 가장 높습니다.

  • CachedReaderEntry 또는 유사한 cache envelope 도입
  • ReaderResponse에서 내부 캐시 필드 제거
  • response cache key에 output options 반영
  • raw cache와 rendered response cache 분리 여부 결정

Step 2. Site Rule Engine 상태 오염 제거

  • SiteRuleConfig 복사본 반환 또는 immutable record 전환
  • disable_css override는 요청 scoped config에만 적용
  • 기존 Contains 기반 룰을 DomainMatchSiteRule로 이전

Step 3. ReadabilityFilter 정확도 보완

  • 중첩 테이블 row 선택 수정
  • inline code 주변 공백 보존
  • code fence newline collapse를 line 기반 state machine으로 변경

Step 4. 회귀 테스트 추가

현재 테스트 프로젝트가 없으므로 최소한 Scraper Infrastructure 단위 테스트 프로젝트를 추가하는 것을 권장합니다.

추천 테스트 케이스:

  • 같은 URL에서 output_images=false 후 output_images=true 요청 시 캐시 응답이 섞이지 않는지
  • disable_css override가 다음 요청으로 전파되지 않는지
  • _cache_etag, _cache_last_modified가 public API 응답에 노출되지 않는지
  • nested table이 외부 table row로 중복 렌더링되지 않는지
  • inline code가 Use x here 형태로 정상 출력되는지
  • https://example.com/?q=amazon.com이 Amazon rule로 매칭되지 않는지

Summary

현재 구현은 Phase 1 목표에 맞춰 방향성은 잘 잡혀 있습니다. 특히 GFM table 변환, 304 처리, site rule 확장, conditional request 도입은 제품 품질을 끌어올리는 유효한 변경입니다.

다만 캐시와 API 응답 모델이 같은 객체를 공유하면서 내부 상태와 public contract가 섞였고, host 단위 rule config 캐시가 mutable 객체를 반환하면서 요청 간 오염 가능성이 생겼습니다. 이 두 부분은 운영 환경에서 실제 사용자 응답 품질을 흔들 수 있으므로 먼저 수정하는 것이 좋습니다.
