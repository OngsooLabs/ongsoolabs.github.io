Credit Usage Guide

AI Reader API exposes usage.credits as response metadata. It helps clients understand whether a reader operation succeeded and how OngsooLabs classifies that operation internally.

RapidAPI is the source of truth for public plan names, prices, request quota enforcement, overage pricing, bandwidth platform fees, billing, and subscription state. This document does not define a separate OngsooLabs pricing table.

RapidAPI Metering

The active RapidAPI configuration has two relevant metering objects:

Object RapidAPI meaning OngsooLabs documentation rule
Requests A call to any endpoint is one request. Treat this as the public quota and billing meter.
Bandwidth Platform Fee RapidAPI platform bandwidth usage. Each unit is 1 MB. Do not describe this as AI Reader API pricing.

Plan names, monthly prices, included request counts, overage rates, enabled/disabled plan state, and bandwidth fee values should be maintained in RapidAPI. Public docs should point users to their RapidAPI dashboard for those values instead of duplicating them.

Response Credit Semantics

For the v1 launch baseline, successful page reads use a simple fixed reader credit model.

Endpoint Success credit policy Failure credit policy
GET /v1/reader 1 credit 0 credits
POST /v1/reader 1 credit 0 credits
POST /v1/reader/chunk Not represented in usage.credits because the success response is the legacy chunk array 0 credits in the standard error envelope

The reader charges the same 1 credit for a successful page read whether the request uses Markdown, text, JSON, optional metadata, optional chunking, static retrieval, browser fallback, or a validated cache refresh.

Do not treat usage.credits as the RapidAPI billing engine. RapidAPI request quota is counted at the gateway level, and the current RapidAPI Requests object says that any endpoint call is one request.

No-Charge Failures

Reader failures return usage.credits = 0.

No-charge failures include:

  • Invalid URLs.
  • Invalid request options or payloads.
  • Unsafe URLs that target local, private, or metadata network ranges.
  • Target-site blocks.
  • Fetch failures.
  • Internal service failures.

RapidAPI gateway-level quota behavior can still apply according to the caller's active RapidAPI plan. The usage.credits field describes OngsooLabs reader credit usage, not every RapidAPI gateway-level accounting rule.

Basic Plan Evaluation

The Basic plan is the current public evaluation path in RapidAPI.

Basic plan baseline:

  • Included request quota is configured in RapidAPI.
  • Intended for evaluation, integration testing, and small prototypes.
  • RapidAPI counts endpoint calls through its Requests object.
  • Successful GET /v1/reader and POST /v1/reader calls return usage.credits = 1.
  • Failed reader calls return usage.credits = 0.
  • Abuse, automated stress testing, or attempts to bypass target-site access controls can be limited or suspended.

The Basic plan is not intended for production ingestion jobs, resale, high-volume crawling, or automated monitoring.

Production Plan Interpretation

Paid plans are controlled by RapidAPI plan configuration, not by this repository.

The public plan should not promise:

  • Guaranteed access to every target website.
  • Guaranteed extraction quality for every page layout.
  • Lowest-price scraping proxy behavior.
  • Browser automation as a standalone product.

The product value is AI-ready data acquisition: clean output, stable response contracts, usage metadata, quality signals, execution metadata, benchmark discipline, and documentation quality.

Future Credit Adjustments

The fixed 1 credit reader model can be revisited after operational data shows a clear need.

Possible future dimensions:

  • Dynamic rendering cost.
  • Very large page size.
  • Advanced extraction profiles.
  • Batch or async ingestion.
  • Structured extraction.
  • Higher support or retention requirements.

Any future change to public reader credit semantics should update this guide, the RapidAPI listing, the README, and the decision log together.
