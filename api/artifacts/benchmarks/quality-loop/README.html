Reader Regression and Challenge Loops

This directory keeps the reviewable inputs, history, and templates for two separate Reader quality responsibilities:

  • the Regression Loop protects behavior that already works;
  • the Challenge Loop discovers realistic public web structures that the Reader does not yet handle well.

Corpus roles

  • live-core.json selects 12 representative cases from the fixed 100 URL Lock. It is a daily observation sample and does not change the release gate.
  • discovery-candidates.json is the active Challenge pool. It contains 1-12 public HTTPS URLs, with at most four each for news, technical-documentation, and product-page.
  • challenge-history.json is the persistent fingerprint-only registry for active, observed, and retired Challenge URLs. It prevents a retired URL from returning under a new case ID without retaining raw URLs.
  • snapshot-manifest.json records deterministic Reader fixtures. Prefer a minimized synthetic fixture for a confirmed pattern. Capturing external HTML requires separate source-rights, privacy, retention, and reuse approval.
  • reader-lock-dataset.json remains the fixed 100 URL release gate. Challenge URLs are never promoted into or exchanged with the Lock automatically.

Challenge admission contract

Reader success is not an admission requirement. A weekly intake may add a candidate only when all of the following are true:

  • it is a realistic public HTTPS page in the supported Reader scope;
  • it does not require login, CAPTCHA, a clear paywall, or access to personal or sensitive user data;
  • it does not target private, loopback, link-local, or otherwise unsafe network assets;
  • its normalized URL fingerprint is absent from the active, observed, retired, and Lock histories;
  • a browser or equivalent independent source confirms that real content exists;
  • ground truth is written before the Reader result is inspected.

Ground truth records sourceObservedAt, short expected title/content markers, optional structural expectations, and an evidence note. It never stores full HTML or extracted content. Existing v1 entries are explicitly marked historical-human-review and should be refreshed during a later weekly intake; new entries use browser evidence.

The initial controlled Challenge tags are:

  • js-heavy
  • long-document
  • code-and-table
  • multilingual
  • redirect-canonical
  • navigation-heavy
  • partial-content-risk
  • browser-fallback

Do not add a tag without an observable selection or evaluation meaning. Balance technical coverage before filling category capacity, and leave slots empty rather than weakening safety or test-value requirements.

Failure classification and recurrence

  • BLOCKED_BY_SITE, UPSTREAM_NOT_FOUND, and UPSTREAM_ERROR_PAGE remain external observations when normal content cannot be compared.
  • Local health, runner, Browser process, transport, and test-execution failures remain infrastructure observations.
  • Missing expected content, partial main content, wrong title/canonical URL, lost code blocks/tables, forbidden block content, or a bad fallback outcome can be product-quality candidates when independent ground truth remains available.
  • A site structure change is not automatically external. If a browser still exposes normal content and only Reader extraction fails, classify it as a product-quality candidate.
  • Only deterministic failures become REGRESSION automatically.

Each product-quality observation records a controlled failurePatternId, such as partial_main_content, missing_expected_content, wrong_title, wrong_canonical, code_block_loss, or table_loss. The runner proposes human review after either:

  • the same URL repeats the same pattern in retained history; or
  • the same controlled pattern appears on at least two different Challenge URLs.

Legacy runs without pattern IDs remain eligible only for same-case recurrence. Cross-URL recurrence never relies on free-form semantic similarity.

Daily execution

Run from the repository root:

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-reader-quality-loop.ps1

The runner validates the v2 Challenge inputs and history, runs solution tests unless skipped, checks local Reader health, executes Live core and active Challenge cases, and writes reader-quality-run.v4 JSON plus a Markdown report under runs/<run-id>/.

The report may propose an improvement review, but the loop never edits product code, creates issues, commits, pushes, deploys, changes authentication/payment/security/database configuration, mutates the Lock, retires a Challenge, or captures an external snapshot automatically.

Weekly Challenge discovery

Once per verified calendar week, discover approximately three to six new candidates across the three content categories, prioritizing under-covered Challenge tags and domains. This is an adjustable operating default, not a quota. Add only vacant active slots, update discovery-candidates.json and challenge-history.json together, and include independent ground-truth evidence in the run summary.

Do not pre-run the Reader as an admission gate. The next complete daily loop is the first Reader quality observation for a newly admitted Challenge.

Retirement and durable regression

  • low_observation_value: access block or permanent-not-found result on three consecutive retained dates.
  • saturated_observation: PASS on seven consecutive retained dates with no new variation.

Removal signals are report-only. Retire a candidate only after explicit human approval, keep its fingerprint in challenge-history.json, and never promote it into the Lock automatically.

For a confirmed product-quality candidate, first reproduce the pattern with a minimized deterministic fixture when possible. Raw external HTML capture stays approval-gated. Product code changes require separate human authorization and must be verified with the target fixture, the original Live URL, and the full 100 URL Lock.

Full Lock gate

Run the full Lock weekly and before/after Reader behavior changes, not as part of every daily observation:

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-reader-quality-loop.ps1 -RunFullLock

The runner keeps the local Reader alive for the optional gate, writes a sanitized full-lock-summary.json beside the daily run, and sets fullLockStatus to PASS or FAIL. A failed Lock gate requires human triage and makes the scheduled run fail.
